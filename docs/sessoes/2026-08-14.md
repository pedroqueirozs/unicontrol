## 2. Importação em massa de fornecedores (PDF do sistema antigo)

Pedro tinha um "Relatório de Fornecedores" exportado em PDF do sistema antigo (M3Soft) — precisava cadastrar tudo de uma vez no UniControl.

### Abordagem
Em vez de transcrever ~380 fornecedores manualmente (alto risco de erro de digitação em dado real de CNPJ), o texto bruto extraído do PDF foi salvo em `scripts/fornecedores-raw.txt` e um parser dedicado (`scripts/import-suppliers.ts`) foi escrito pra interpretar esse texto — que tem um formato de linhas meio bagunçado (resíduo de como o PDF foi gerado: rótulo tipo "BAIRRO:"/"CIDADE:"/"UF:"/"E-MAIL:" às vezes aparece colado com o valor de outro campo). O parser foi ajustado e conferido por amostragem contra o texto original várias vezes antes de rodar de verdade.

- Roda em **modo simulação por padrão** (só mostra o que seria criado, não grava nada) — só aplica de verdade com `--apply`, mesmo padrão dos outros scripts do projeto (`scripts/import-products.ts`, `scripts/backfill-movement-balances.ts`).
- **CNPJ/CPF é obrigatório** (RN-20) — dos ~376 fornecedores do relatório, 6 não tinham documento válido (alguns eram claramente placeholders do sistema antigo, tipo "TRANSPORTADORA" com CNPJ só de zeros, ou "O PROPRIO") e ficaram de fora, listados explicitamente no log do script.
- **Detecção de duplicado por CNPJ** foi adicionada depois de rodar a simulação contra produção: 2 fornecedores do relatório já existiam no banco (cadastrados manualmente, com nome diferente — ex: "J. A. DE SILVA METAIS" no relatório antigo é o mesmo CNPJ do "Terrafogo e Bronze" já cadastrado). O script passou a checar isso e pular em vez de duplicar.
- Endereço (rua/número/bairro) é o campo com parsing mais "melhor esforço" — funciona bem quando o endereço original tem vírgula separando rua de número, mas em endereços sem vírgula às vezes número/bairro não separam do nome da rua (fica tudo no campo rua, sem quebrar o cadastro). Cidade, UF, CNPJ/CPF são bem mais confiáveis.

### Execução
1. Simulação e depois aplicação (`--apply`) no **banco de dev** — 370 criados, 6 ignorados.
2. Simulação e depois aplicação no **banco de produção** — feito passando a `DATABASE_URL` de produção só como variável de ambiente do comando (`DATABASE_URL="..." npx tsx scripts/import-suppliers.ts --apply`), **sem editar o `.env`** (evita o risco de esquecer revertido e o ambiente de dev passar a apontar pra produção por engano). Produção já tinha 7 fornecedores cadastrados manualmente; resultado final: **375 fornecedores** (7 + 368 importados, os 2 duplicados foram pulados).

### Decisão importante: os arquivos NÃO foram commitados
O repositório `unicontrol` no GitHub é **público** (confirmado via API do GitHub nesta sessão). `fornecedores-raw.txt` tem CNPJ/telefone/endereço de ~370 fornecedores — a maioria é dado de empresa (CNPJ é registro público, sem problema), mas um punhado são pessoas físicas (CPF + endereço pessoal, ex: "Marcos Lima de Vasconcelos", "Samuel Lima de Vasconcelos"). Como o repo é público, isso seria dado pessoal exposto publicamente no GitHub.

**Decisão do Pedro: não commitar nada por enquanto.** `scripts/import-suppliers.ts`, `scripts/check-existing-suppliers.ts` e `scripts/fornecedores-raw.txt` continuam só no filesystem local, fora do git — os dados já estão nos dois bancos (dev e produção), então não fazia falta também morarem pra sempre no histórico do Git. Se decidir commitar os scripts (sem o `.txt` com dados pessoais) depois, é só pedir.
